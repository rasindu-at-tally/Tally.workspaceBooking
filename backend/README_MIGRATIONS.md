# Database Migrations Guide

This project uses **Alembic** for database migrations with **PostgreSQL**.

## Prerequisites

- PostgreSQL database running
- Virtual environment activated
- Dependencies installed (`pip install -r requirements.txt`)

## Database Configuration

Database connection is configured in `app/core/config.py`:
```python
DATABASE_URL = "postgresql://postgres:postgres@localhost:5432/office_booking"
```

You can override this using a `.env` file.

## Migration Commands

### Create a new migration (autogenerate)
```bash
alembic revision --autogenerate -m "description_of_changes"
```

### Apply migrations
```bash
# Upgrade to latest version
alembic upgrade head

# Upgrade one version
alembic upgrade +1

# Downgrade one version
alembic downgrade -1

# Downgrade to specific version
alembic downgrade <revision_id>
```

### Check current migration status
```bash
alembic current
```

### View migration history
```bash
alembic history
```

### Show specific migration
```bash
alembic show <revision_id>
```

## Initial Setup

If starting fresh:

1. **Create the PostgreSQL database**:
```bash
psql -U postgres
CREATE DATABASE office_booking;
\q
```

2. **Run migrations**:
```bash
cd backend
source venv/bin/activate
alembic upgrade head
```

3. **Seed the database** (optional):
```bash
python seed_data.py
```

## Common Issues

### "Table already exists" error
If you get this error, it means tables were created using `Base.metadata.create_all()` instead of migrations.

**Solution**: Drop all tables and recreate using migrations:
```bash
# In psql
DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
GRANT ALL ON SCHEMA public TO postgres;
GRANT ALL ON SCHEMA public TO public;

# Then run migrations
alembic upgrade head
```

### Migration not detecting changes
Make sure:
1. All models are imported in `alembic/env.py`
2. Models inherit from `Base`
3. You've saved the model file

## Best Practices

1. **Always use migrations** for schema changes
2. **Review autogenerated migrations** before applying
3. **Test migrations** in development before production
4. **Commit migration files** to version control
5. **Never edit applied migrations** - create new ones instead
